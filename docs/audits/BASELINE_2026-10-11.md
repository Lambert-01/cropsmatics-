## 2. Production bug reproduction (read-only against configured Neon DB)

Pointed the app at `DATABASE_URL` from `.env` exactly as a deployment would, no
writes, no migrations:

| Endpoint | Before | After fix (`fa3977f`) |
|---|---|---|
| `/api/v1/health` | 200 | 200 |
| `/api/v1/health/readiness` | 200 `status: degraded` | 200 `status: degraded` (honest — see §3) |
| `/api/v1/data/version` | **500** `AttributeError: 'str' object has no attribute 'version'` at `canonical_repository.py:171` | **200**, `source: postgres`, version `0.2.0-535efe5d2bd75b51` |
| `/api/v1/data/coverage` | 200, 8 periods (2024A–2026B), 3,738 productivity rows, 1,477 observations | unchanged |
| `/api/v1/meta/indicators` | 200 (but would 500 with serving DB — same defect class in `indicator_rows()`) | 200 verified with serving DB |

**Root cause (verified):** on a SQLAlchemy Core connection (no ORM session),
`connection.execute(select(DatasetVersion))` returns rows of raw column
values; `scalar_one_or_none()` therefore yielded the `version` **string** and
attribute access raised. `indicator_rows()` had the identical defect via
`.scalars()`. Unit tests could not catch this: `tests/conftest.py` pins
`DATABASE_URL` to an unreachable port, so the projection code never ran.

**Fix:** explicit column projections through `.mappings()` in both reads
(`services/api/app/repositories/canonical_repository.py`), plus regression
tests on an in-memory database (`tests/test_canonical_row_handling.py`, 7
tests) that were proven to fail against the pre-fix code.
